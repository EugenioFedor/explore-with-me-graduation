# Explore With Me — recommendations

Проект разделяет бизнес-функциональность на независимые Spring Boot сервисы. Внешний API остаётся единым: клиент обращается к API Gateway на порту `8080`, а Gateway маршрутизирует запрос в нужный сервис через Eureka.

## Архитектура

- `infra/discovery-server` — Eureka Service Discovery.
- `infra/config-server` — централизованная конфигурация. Конфигурации сервисов находятся в `infra/config-server/src/main/resources/config`.
- `infra/gateway-server` — единая точка входа, порт `8080`.
- `core/user-service` — управление пользователями, отдельная БД `user-db`.
- `core/event-service` — события, категории и подборки, отдельная БД `event-db`.
- `core/request-service` — заявки на участие, отдельная БД `request-db`.
- `core/comment-service` — дополнительная функциональность комментариев, отдельная БД `comment-db`.
- `stats-service/collector` — gRPC-приём действий и публикация Avro в Kafka.
- `stats-service/aggregator` — инкрементальный расчёт сходства мероприятий.
- `stats-service/analyzer` — PostgreSQL-история взаимодействий, сходства и gRPC-рекомендации.
- `stats-service/stats-proto`, `stats-avro` — схемы и генерация кода; `stats-client` — gRPC-клиенты.
- Kafka — топики `stats.user-actions.v1` и `stats.events-similarity.v1`.

Сервисы не используют JPA-связи между разными базами. Вместо объектов других сервисов хранятся идентификаторы (`initiatorId`, `requesterId`, `eventId`, `authorId`). Межсервисные обращения выполняются через OpenFeign, а адреса экземпляров разрешаются через Eureka.

## Внутренний API

Внутренние endpoint'ы не предназначены для внешних клиентов и используются Feign-клиентами:

- `GET /internal/users/{userId}` — получить пользователя для event/request/comment-service.
- `GET /internal/events/{eventId}/request-info` — данные события, необходимые request-service: инициатор, статус, лимит участников и признак модерации.
- `GET /internal/events/{eventId}/comment-info` — проверить событие и его статус для comment-service.
- `GET /internal/requests/events/{eventId}/confirmed-count` — число подтверждённых заявок события.
- `POST /internal/requests/events/confirmed-counts` — числа подтверждённых заявок сразу для набора событий; пакетный метод исключает N+1 сетевых запросов.
- `GET /internal/comments/events/{eventId}/published-count` — число опубликованных комментариев события.
- `POST /internal/comments/events/published-counts` — числа опубликованных комментариев сразу для набора событий.

При недоступности request-service или comment-service event-service возвращает для соответствующих счётчиков значение `0`, поэтому публичное чтение событий не должно падать только из-за недоступности этих сервисов. При недоступности user-service публичное представление события сохраняет id инициатора и возвращает пустое имя.

## Внешний API

Спецификация основного внешнего API находится в корне проекта: `ewm-main-service-spec.json`. Описание нового gRPC API: `stats-service/README.md`. Postman-коллекции находятся в каталоге `postman`.

## Запуск

```bash
mvn clean verify
docker compose up --build -d
docker compose ps
```

После запуска внешний API доступен через Gateway: `http://localhost:8080`.

Перед сдачей рекомендуется выполнить Maven-тесты, затем Postman-коллекции через порт `8080`, после чего проверить деградацию системы при последовательной остановке `comment-service`, `request-service` и `user-service`.


## Этап 3: рекомендации

Требуются JDK 21, Maven 3.9.9 и Docker Compose v2. Protobuf/gRPC и Avro Java-классы генерируются Maven при сборке; вручную добавлять сгенерированные файлы не нужно.

Вес просмотра — `0.4`, заявки — `0.8`, лайка — `1.0`. Для пары пользователь/мероприятие хранится максимальный вес; повторные просмотры или лайки не суммируются. `rating` во всех DTO мероприятий — `double`, сумма этих максимальных весов для мероприятия. Вложенные мероприятия в подборках также получают рейтинг из Analyzer.

- `GET /events` — список, без отправки просмотра; сортировка `EVENT_DATE` или `RATING`.
- `GET /events/{id}` — обязателен заголовок `X-EWM-USER-ID`; отправляет просмотр опубликованного события.
- `GET /events/recommendations?size=10` — тот же заголовок, список `EventShortDto` в порядке персонального прогноза. Без истории возвращается `[]`. Поле `rating` содержит общий рейтинг, а не прогноз для одного пользователя.
- `PUT /events/{eventId}/like` — тот же заголовок; успешный ответ `204`. Поскольку отдельного учёта фактического посещения в проекте нет, право на лайк определяется подтверждённой заявкой на опубликованное событие. Отсутствующая, ожидающая, отклонённая или отменённая заявка даёт `400`.
- `POST /users/{userId}/requests?eventId=...` — после проверки и сохранения заявки отправляет `ACTION_REGISTER`. При ошибке Collector транзакция БД откатывается.

Обработка Kafka асинхронная: обновлённый рейтинг и рекомендации появляются после обработки сообщений. Collector отвечает успешно только после подтверждения записи брокером. Недоступность обязательного рекомендательного сервиса возвращает `503`, а не успешный ответ с выдуманным рейтингом.

Collector, Aggregator и Analyzer получают конфигурацию через Config Server, адрес которого находят в Eureka. Collector и Analyzer регистрируют случайный gRPC-порт (`grpc.server.port=0`) в метаданных Eureka `gRPC_port`. Клиенты используют `discovery:///collector` и `discovery:///analyzer`. HTTP-порт внутри их контейнеров — `8080`, только для healthcheck; внешнее приложение доступно через Gateway `8080`.

Kafka работает в KRaft-режиме без ZooKeeper. `kafka-init-topics` создаёт оба топика с одной партицией. Снаружи Docker bootstrap-адрес — `localhost:9092`, внутри — `kafka:29092`. БД Analyzer доступна с хоста на `6541`; остальные БД сохраняют порты `6542–6545`. Данные Kafka и БД сохраняются в Docker volumes. Не используйте `docker compose down -v`, если их нужно сохранить.

### Пересчёт сходства и восстановление

Частные суммы обновляются на разницу весов, ключ пары всегда `(min(id), max(id))`. История Kafka сохраняется без ограничения срока. После перезапуска единственный экземпляр Aggregator читает историю с начала и восстанавливает матрицу и суммы; в период восстановления рекомендации могут меняться. Analyzer делает идемпотентные upsert и хранит максимальный вес отдельно от времени последнего действия.

В материалах есть два описания публикации: полный пересчёт всех пар и пропуск пары, если текущий пользователь не взаимодействовал со вторым мероприятием. Проверяющий инструмент курса требует второй вариант. Поэтому `stats.aggregation.publish-all-pairs=false` в `aggregator.properties` — режим по умолчанию для сдачи. Все суммы поддерживаются, но сообщения публикуются только для пар с общим взаимодействием текущего пользователя. Коэффициент другой пары обновится при следующем относящемся к ней действии.

Для строгого обновления всех коэффициентов при изменении знаменателя задайте `stats.aggregation.publish-all-pairs=true`. Этот режим соответствует полной формуле, но публикует больше сообщений, чем ожидает текущий инструмент курса. Оба режима проверены unit-тестами.

Для персонального прогноза выбираются кандидаты из сходств с последними `stats.recommendations.recent-limit=100` взаимодействиями, исключаются все уже просмотренные мероприятия. Прогноз считается по `stats.recommendations.neighbors-limit=10` ближайшим просмотренным соседям. Оба ограничения настраиваются в `analyzer.properties`. Нулевые сходства не используются; при отсутствии подходящих соседей рекомендация не выдаётся.

### Проверки

```bash
mvn clean verify
mvn -Pcheck verify
docker compose up --build -d
python3 scripts/recommendations-smoke.py
newman run postman/ewm-main-service.json
newman run postman/feature.json
```

Сквозной smoke-тест создаёт собственных пользователей, категорию и три мероприятия, проверяет просмотр/регистрацию/лайк, рейтинг, рекомендации и ошибки. Тестовые записи сохраняются для диагностики; используйте отдельную тестовую БД. Внешний API статистики `/hit` и `/stats` заменён gRPC, поэтому устаревшая HTTP-коллекция статистики удалена. Для проверки gRPC/Kafka в курсовом CI выберите ветку `recommendations` и режимы `COLLECTION`, `AGGREGATION`, `ANALYZE`.
